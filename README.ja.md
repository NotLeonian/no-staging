# no-staging

[English](README.md)

`no-staging` は、Git リポジトリで作業するエージェントに、作業ツリーで加えた変更をステージしないよう指示する、明示的に呼び出すための Agent Skill を収録した Codex プラグインです。

## 概要

このスキルを有効にすると、エージェントは作業ツリー内のファイルを作成、編集、移動、削除できますが、Git インデックスを意図的に変更するコマンドは実行しません。

このスキルは、ユーザーが `$no-staging` を明示的に呼び出した場合にのみ使用します。

作業を終えるときには、追加、変更、移動、削除したファイルを報告し、それらをステージしていないことを明記します。

## 動作

スキルが有効な間、エージェントは次の規則に従います。

- ファイルをステージしません。
- `git add`、`git stage`、`git commit`、`git mv`、`git rm` など、Git インデックスを意図的に変更するコマンドを実行しません。
- 作業を始める前からステージされている変更は、そのまま残します。
- 作業ツリー内のファイルは通常どおり作成、編集、移動、削除できます。
- `git status`、`git diff`、`git diff --stat`、`git ls-files` など、状態や差分を調べる Git コマンドは使用できます。
- タスクを完了するためにステージする必要がある場合は作業を止め、明示的な許可を求めます。
- 最後に、追加、変更、移動、削除したファイルと、それらをステージしていないことを報告します。

一時的にステージしてから元に戻す操作も行いません。

## インストール

リポジトリを取得し、その絶対パスをローカルのマーケットプレイスとして登録してから、プラグインをインストールします。

```console
git clone https://github.com/NotLeonian/no-staging.git
codex plugin marketplace add /absolute/path/to/no-staging
codex plugin add no-staging@no-staging
```

インストールした後は、新しい Codex スレッドを開始してスキルを読み込んでください。

スキルだけを使う場合は、スキルのディレクトリをローカルの Agent Skills ディレクトリへコピーします。

```console
mkdir -p "$HOME/.agents/skills"
cp -R /absolute/path/to/no-staging/skills/no-staging "$HOME/.agents/skills/"
```

## 使い方

Git リポジトリでの作業を依頼するときに、スキルを指定します。

```text
$no-staging

必要な変更を加えてください。
ただし、どの変更もステージしないでください。
```

通常の Git タスク、変更をステージしないよう求める依頼、ステージングに関するリスク、またはこのスキルへの言及だけを理由に、このスキルが自動的に選ばれることはありません。
スキル名を自然言語で指定して使用を求めても、`$no-staging` を含めない限り、このスキルは呼び出されません。
このスキルについての相談、保守、インストール、設定も、このスキルの呼び出しには当たりません。

## このスキルが保証しないこと

このスキルはエージェントへの指示であり、ステージングを技術的に遮断する仕組みではありません。

- Git フック、sandbox、権限を管理する仕組み、OS のアクセス制御ではありません。
- ホストがスキルを読み込み、エージェントが指示に従っている間だけ作用します。
- ユーザー、IDE、バックグラウンドのプロセス、別のエージェント、別のセッションが Git インデックスを変更することは防げません。
- スキルを有効にする前からステージされている変更は、元に戻したりステージから外したりしません。
- 作業ツリー内でファイルを作成、編集、移動、削除することは許可します。
  ファイルを保護したり、バックアップを作成したりするスキルではありません。
- Git 以外のバージョン管理システムには適用しません。
  また、ステージングと関係のない書き込みを広く禁止するものでもありません。
- Git 全体を安全に操作するためのポリシーではありません。
  ステージングと関係のない操作には、ホストが定める別の指示や安全策が適用されます。
- 外部ツールが予期せず Git インデックスを変更する場合、このスキルだけではその変更を防げません。
- ステージしなければ完了できないタスクでは、ユーザーから明示的な許可を得るまで作業を進められません。

読み取り専用として扱われる Git コマンドでも、Git の設定によっては FSMonitor、filter、外部 diff、pager などの補助プログラムを起動する場合があります。
また、ファイルの内容をステージしなくても、インデックスのメタデータを更新する場合があります。
このスキルは、意図したステージングの状態を保つためのものであり、`.git/index` の内容が一切変わらないことや、状態を調べるコマンドに副作用がないことまでは保証しません。
そのような保証が必要な場合は、別の技術的な制御、信頼できる実行ポリシー、または `codex-read-only-approver` のような補助的な仕組みを併用してください。

最後に「ファイルをステージしていない」と報告しても、それはエージェント自身の操作について述べているだけです。
別の要因によってステージされた変更がないことまでは証明しません。

## 確認する

作業の前後でステージングの状態を調べます。

```console
git status --short
git diff --cached --name-only
```

作業を始める前からステージされている変更がある場合、2 番目のコマンドの出力は空になりません。
その場合は、作業の前後で出力を比較してください。
これらのコマンドは状態を調べるための例であり、ステージングを強制的に防ぐものではありません。

## リポジトリを検証する

公開する前に JSON ファイルを検証し、Markdown とスキルの内容を確認します。

```console
python3 -m json.tool .codex-plugin/plugin.json
python3 -m json.tool .agents/plugins/marketplace.json
python3 ~/.codex/skills/.system/plugin-creator/scripts/validate_plugin.py .
git diff --check
```

プラグインの検証ツールを実行するには、Codex のシステムスキルと、それが利用する Python の依存関係が必要です。
利用できない環境では省略できます。
このツールは、収録しているスキルのマニフェストも確認します。

この検証で確認できるのは、プラグインとスキルの静的な構成です。
エージェントの動作を再現したり、エージェントがスキルに従うことを証明したりはしません。

## テスト

Git の作業ツリーのルートで、リポジトリのテストを実行してください。
テストでは Git と、`tests/requirements.txt` でバージョンを固定した Python パッケージを使います。
先にパッケージをインストールしてください。

```console
python -m pip install --disable-pip-version-check -r tests/requirements.txt
python -B -m unittest discover -s tests -p 'test_*.py' -v
```

テストでは、JSON ファイルを解析できること、プラグインとマーケットプレイスのメタデータが一致すること、ホストがスキルを検出できる構成になっていること、`no-staging` の主要な指示が残っていることを確認します。
Python の検査で使う設定が正しいことも確認します。
Markdown 文書内の相対リンクを検査するときは、`.md` または `.markdown` という拡張子を大文字と小文字を区別せずに照合します。
その条件に合うファイルのうち、Git が追跡しているものと、未追跡でも Git が無視していないものを作業ツリー全体から集め、リンク先が存在することを確認します。

Markdown 文書へのハイパーリンクに空ではないフラグメントがある場合は、そのフラグメントが、見出しから生成したアンカーか、`<a name>` で明示したカスタムアンカーと一致することも確認します。
見出しからアンカーを生成するときは、GitHub が公開している規則に従います。
文字を小文字にし、半角スペースをハイフンへ置き換えます。
ASCII のハイフンやアンダースコアなど、GitHub が残す文字を除いて、句読点やほかの空白は取り除きます。
マークアップを除き、同じアンカーが重なる場合は番号も加えます。
この処理では、GitHub が実際に描画した結果を取得して照合しません。
そのため、GitHub 側の挙動が今後変わった場合や、一般的でない Unicode の文字を含む場合には差が生じることがあります。
`?plain=1#L10` のように Markdown のソースにある行を指す場合は、見出しのアンカーとは比較せず、指定した行がファイル内にあることを確認します。
HTML や SVG など、Markdown 以外のファイルが持つフラグメントは検査しません。
ブラウザが本文中の文字列を探すために使う `#:~:text=example` 形式も検査しません。
`/` から始まるパスは、リポジトリのルートを基準とするローカルパスとして扱います。
Web サイトのルートを基準とするパスを使う場合は、絶対 URL で記述してください。

リンクは `markdown-it-py` の CommonMark preset で解析します。
別の Markdown 拡張が必要な構文は解析しません。
テストの対象はリポジトリの構成と、スキルに含まれる静的な指示です。
エージェントの動作は再現しないため、エージェントがスキルに従うことまでは証明しません。

GitHub Actions は、pull request と `main` への push で自動的に実行されます。
pull request の元ブランチが `main` 以外であれば、そのブランチへ push しても、push イベントから別の実行は始まりません。
手動でも実行できます。
各実行では、バージョンを固定したパッケージをインストールし、Python 3.13 を使用して Windows、macOS、Ubuntu で同じテストを実行します。

Ruff、mypy、Pyright で Python コードを検査するためのコマンドは、[CONTRIBUTING.md](CONTRIBUTING.md) に記載しています。
`tests/requirements.txt` では、これらのツールと Markdown の解析に使うパッケージのバージョンを固定しています。

## リポジトリの構成

```text
no-staging/
├── .github/
│   └── workflows/
│       └── ci.yml
├── .agents/
│   └── plugins/
│       └── marketplace.json
├── .codex-plugin/
│   └── plugin.json
├── skills/
│   └── no-staging/
│       ├── agents/
│       │   └── openai.yaml
│       └── SKILL.md
├── tests/
│   ├── pyproject.toml
│   ├── requirements.txt
│   └── test_repository.py
├── .editorconfig
├── .gitattributes
├── .gitignore
├── CONTRIBUTING.md
├── LICENSE
├── README.ja.md
├── README.md
└── SECURITY.md
```

プラグインのメタデータは `.codex-plugin/plugin.json` にあります。
マーケットプレイスの定義は `.agents/plugins/marketplace.json` にあり、スキルの指示は `skills/no-staging/SKILL.md` にあります。
